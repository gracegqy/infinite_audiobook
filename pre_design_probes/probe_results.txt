PROBE 1b — mid-sentence pause bug (Grace's report 2026-07-18): ROOT-CAUSED + FIXED
Script: probe1b_pause_fix.py
- Cause: probe scripts fed Kokoro text with hard line-wraps; KPipeline splits chunks on
  newlines, so every wrapped line ended in a padded chunk boundary mid-sentence
  (HORROR literal had 26 embedded newlines -> 27 chunks). NOT a Kokoro quality issue.
- Fix: collapse whitespace runs to single spaces before synthesis. Chunks 27->7 (EN),
  5->1 (ES). Remaining ≥500ms gaps verified punctuation-aligned: chunk-boundary joins
  (~0.85s) match Kokoro's own natural sentence pauses within a chunk (0.8-0.9s);
  0.5-0.6s gaps sit at Poe's dashes/semicolons. Structure is audiobook pacing, not
  random breaks.
- PIPELINE LESSON (promote to Phase 2 design): the clean stage MUST unwrap hard-wrapped
  lines within paragraphs (Gutenberg wraps at ~70 cols) or every story gets this bug.
- New files for Grace's re-listen: probe1/horror_usher_af_heart_fixed.wav,
  horror_usher_am_michael_fixed.wav, spanish_quiroga_ef_dora_fixed.wav (+ _fixed.m4a).

PROBE 5 — Phone playback reality (iOS Safari over Tailscale)
Status: RESUME RETEST PASSED (Grace, 2026-07-18) · remaining sub-checks: lock-screen
controls, ≥5-min backgrounded playback, speed selector honored — no recorded evidence yet
Script: probe5_phone_server.py + probe5_static/index.html

- 2026-07-18 earlier: Tailscale was not installed (contradicted brief assumption).
  RESOLVED same day: Grace installed it on Mac + iPhone; Mac's Tailscale IP is
  100.117.147.107 (verified via Tailscale.app CLI + curl below).
- Grace's first phone attempt showed a blank page because the server wasn't running
  bound to the Tailscale IP. Now running: probe5_phone_server.py 100.117.147.107,
  verified from the Mac: GET / -> 200; Range request on the fixed m4a -> 206 with
  correct content-range. Log: data/interim/probe5_server.log.
- Test page now includes a playback-speed selector (0.75-2x via audio.playbackRate,
  with on-page logging of whether iOS honors it) — probes requirement R13.
- FIRST PHONE RUN (Grace, 2026-07-18): everything worked on first open — play, scrub,
  ±15s. After kill+reopen: audio restarted at 0 and scrubbing went dead.
  ROOT CAUSE: iOS Safari silently drops currentTime seeks issued before metadata is
  loaded, and gates media loading behind a user gesture; audio.duration is NaN until
  then, so the scrubber's fraction-of-duration math no-ops too. Desktop queues early
  seeks, which is why it worked from the Mac.
  FIX (live on the server): resume target is queued and applied on loadedmetadata
  (backup: on `playing`); scrubber guarded + logs when metadata isn't ready;
  localStorage writes suppressed until the pending resume applies (no position
  clobbering by early timeupdate ticks at 0).
  PHASE 4 DESIGN LESSON: resume must be applied loadedmetadata-or-later on iOS —
  never at page init. (Real app stores position server-side, not localStorage.)
  RETEST (Grace, 2026-07-18): PASSED — kill Safari + reopen resumes at saved position
  and scrubbing works ("the session-resume issue is fixed now"). The loadedmetadata
  fix holds on the real target. Server re-verified same day from the Mac: GET / -> 200,
  Range bytes=100000-100999 on probe1/horror_usher_af_heart_fixed.m4a -> 206 with
  correct content-range (1,154,657 total).
  SECOND BUG (Grace's report, 2026-07-18, after the ≥5-min backgrounding attempt):
  play immediately auto-paused on reopen. Cause: the 2:30 sample PLAYED TO THE END
  during backgrounding; timeupdate had saved position ≈ duration, so the next open
  resumed to the end and iOS fired ended->pause instantly. Not a playback failure —
  faithful resume to a saved end-of-file position. Fix (live on the server): resume
  targets within 2s of duration are discarded (restart at 0), saved position cleared
  on `ended`, pause log now records currentTime + ended flag, play() rejections logged.
  PHASE 4/5 DESIGN LESSON: a story reaching `ended` must clear/complete its resume
  position (and mark the story read) — never store end-of-file as a resume point.
  NOTE: this reframes the backgrounding check. Every probe sample is shorter than
  5 min (fixed m4a 2:30; probe2 concat ~1:16), so "backgrounded ≥5 min" can't be met
  literally — and if the end-of-file diagnosis is right, the audio KEPT PLAYING while
  locked until the story ended, which is precisely what the check exists to prove.
  Confirmation: on next open, the log line "saved position … at the end — restarting
  from 0" retroactively proves played-to-end-while-backgrounded.
  STILL UNANSWERED (no recorded evidence from either phone run):
    (a) lock-screen / Media Session controls (artwork+title show? play/pause/±15s
        from lock screen work?)
    (b) backgrounded/locked playback — does audio keep playing unattended to the end
        of the story? (Likely already true per the end-of-file evidence above; the
        "restarting from 0" log line on next open confirms it.)
    (c) speed selector: does iOS actually honor audio.playbackRate at 0.75/1.5/2x?
        (R13; the on-page log records the effective rate)
  These decide Phase 4's Media-Session/PWA scope; probe 5 closes when Grace reports
  all three.
